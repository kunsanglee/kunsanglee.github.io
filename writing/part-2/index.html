How I redesigned our in-house AI agent

By Kunsang Lee. Translated from the Korean original on Medium; it describes the system and my role as they were at the time of writing. I left the company in November 2026.

I’m a backend developer on this team, and I was one of the people who used to get the “can you check this?” questions from other teams. In Part 1, I built an agent that answers those questions in Slack, and said I would watch the results over time.

I put that agent in our code-question channel and watched it for 15 weeks. In that time it answered 235 threads, 216 of them asked by 11 colleagues. More than half of the colleagues’ questions came from non-developer roles such as product planning. Across all 235, the median time to first answer was 96 seconds, and questions posted outside working hours were also answered in a median of 99 seconds. In this post I’ll show those numbers, and then describe how I changed the structure again after looking at them.

About 38 hours of developer time, if people had answered right away

Say a product planner asks, “How many members have no thumbnail, excluding those who deleted their accounts?” To answer right away, a developer has to stop what they’re doing, write and run the SQL with an AI coding tool, and tidy up the result, which takes around 5 minutes. Then it takes another 5 minutes to get back to the original task and regain focus.

If a client developer asks, “Could I see an example response for this API?”, it takes a backend developer 5 minutes to check. If the question is “What are all the conditions under which a new-message push is sent?”, someone spends 5 minutes opening the code and working out the conditions. Either way, the 5 minutes to get back to the original task come on top.

With an AI coding tool such as Claude Code, checks like these usually finish within a few minutes, so I put handling time at 5 minutes on average. I read each question and sorted the 235 threads by type, with the result below.

I assumed a developer answered all 226 threads (excluding “Other”) the moment they came in, and put the time per thread at about 10 minutes: 5 to handle it and 5 to get back to work. 226 threads times 10 minutes is about 38 hours, or about 5 working days. Dividing 38 hours by the 75 working days in 15 weeks gives about 30 minutes a day, and half of that, about 19 hours, is time spent getting back to the interrupted task.

This number is an estimate built on assumptions, not a measurement. The 5 minutes of handling and 5 minutes of recovery are on the short side, and I left out the time the asker spent waiting, because that varies by person and situation. In the other direction, assuming a developer would have answered all 226 right away may overstate it, so please read this number only as a sense of scale.

I let people hand off “do this,” not just “check this”

The original agent only answered what it was asked. Watching the team use it, I came to think that if the agent were a real teammate in Slack, there would be more to ask of it than checks. If you’d asked a colleague “Which API does this screen call?”, you might follow up with “Then could you make a ticket for this?” After “Why is this value like this?”, you could hand over “Fix it and open a PR.”

The team hadn’t asked for these features, but I thought a colleague should be able to take requests like these, so I added ticket and PR creation and production data queries one at a time.

Here is what you can now ask for in a thread.

Of these, database writes were added later as a follow-on, and search over past conversations was added to find things that were said outside the thread.

But as I added these features to the Part 1 agent one by one, more and more code went into tracking how far a conversation had got. Each task had stages in the database such as “awaiting approval → in progress → done,” and code defined what could be said at each stage (a state machine). Approval was accepted only when the user sent the exact phrase approve <code> that the agent had given them; for anything else, the model picked between cancel and revise and wrote that down, and the code read that line and moved the stage. Every time a flow was added, such as creating tickets from a planning draft, code work, or account linking, the stages and branches in the code grew with it.

Looking back, the roles had been reversed. Understanding what people mean is what the model does best, and the code was doing that job. Meanwhile, limits that absolutely had to hold were only written down as prompt instructions. The model follows instructions most of the time, but “most of the time” is no guarantee of “always.”

So I changed the principle. The model judges what people mean; the code decides what may be executed. The code doesn’t try to work out whether what a person wrote is an approval. It keeps only facts such as who posted where and when, and whether the agent posted a given message. Whether a tool may run is decided from those facts alone.

I redesigned it as one session per thread

The goal of the redesign was for the agent to feel like one more colleague on the team. With a colleague, you carry on a conversation casually in a thread, and when someone posts in a channel without addressing anyone, whoever knows the answer replies first. I wanted people to be able to treat the agent the same way. So in a thread where a conversation has started, the agent understands follow-ups without a mention, and in channels it replies to posts that weren’t addressed to it, if it can help.

There was one more reason to put the agent in Slack as a colleague. With a tool like Claude Code, each developer can have a model read the repositories on their own machine and find out for themselves how iOS, Android, web, and backend each implement something. For looking things up while developing alone, that’s enough. But to discuss the result with someone else, you have to carry what you asked and what you got back over to Slack and explain it again.

When you ask the agent in a channel, the question and answer are in the thread from the start. Anyone in the channel can read along right there and follow up directly, so nobody has to re-explain the context. I saw more value in the team being able to see the questions and answers together.

I attached one Claude Agent SDK session to each Slack thread. The Claude Agent SDK is Anthropic’s library for calling Claude Code from inside your own program; it runs the loop of reading files, searching, calling tools, looking at the results, and deciding again. A session is a running conversation with the model that keeps the earlier exchange in context. In this post I’ll call the session attached to a thread a thread session. A thread session reads everything that arrives in its thread (what people say, other bots’ posts, reactions, and edits), and the model decides whether to reply and what to do.

My bot code does three things.

  • When a session starts, it decides which tools to give it.
  • Every time the model calls a tool, it decides whether to allow it.
  • From what comes back, it records the session ID and usage.

There were five design decisions.

The unit of conversation is the thread

The team was already keeping one topic to one thread. Rather than invent a new unit of conversation, I used the thread as it was. The bot code stores each thread paired with its session ID in the database, and feeds posts arriving in the same thread into that session in order. Within one thread only one request runs at a time, so there’s no separate ordering to manage, and when the agent is restarted, the bot code continues the conversation from the stored session ID.

A thread session starts with a channel post that mentions the agent, and later posts in that thread are read by the same thread session even without a mention. I cover auto-reply, where the agent answers posts that weren’t addressed to it, separately below.

Slack can’t render Markdown tables as tables, so the agent answers with lists instead, and converts formatting such as bold to Slack’s own style before posting.

The model judges meaning; the code decides whether to execute

When the model calls a tool, a policy function checks the call just before it actually runs. The policy function is the code that decides whether a tool may run, and it looks at the following.

  • The tool the model is trying to call, and its arguments. For example, “create ticket” with the ticket’s title and body.
  • The order of events in this thread: whether the agent has posted in the thread, whether a person has replied after the agent’s last post, and whether the same request has already been executed.
  • For a production database query, the estimated cost, measured in advance from the query plan.
  • Whether the session was started by a person or by an error alert.
  • Settings such as which projects allow deletion and which repositories allow automatic fixes.

What people said is not passed to the policy function. From this information it returns only allow or deny, with the reason; it doesn’t call any external system. Because it doesn’t look at the conversation’s content, the same sequence of events always produces the same result, and it can be tested without a real Slack or database.

Tools are divided into read tools and write tools, and the conditions for running them differ by kind. Apart from the tool that posts replies to Slack, write tools (such as the ones that create a ticket or comment on a PR) run only when all three of the conditions below are met. The one exception is automatically fixing an error alert, which I describe separately below.

  1. The agent has posted a draft in this thread.
  2. A person has approved that draft in a reply.
  3. There is no execution record showing that the same request has already been handled.

The code checks condition 3; conditions 1 and 2 are shared between the model and the code. The model decides what to post as a draft and whether a reply is an approval. If the reply is “Looks good, go ahead,” the model calls the tool; if it’s “Just change the title,” it revises the draft and posts it again; if it’s “No,” it doesn’t call the tool. The code doesn’t look at what the posts say. It checks only whether the agent has posted in this thread and whether there is a reply from a person after that last post. This way, even if the model tries to execute on its own without a reply, it is blocked.

The figure below gathers how the policy function decides for each kind of tool. Ticket deletion and PR merges add one more check on top of the three conditions, and for database queries the decision depends on which database it is and whether it’s a read or a write.

If the model tries to create a ticket straight away on the first message of a new thread, the policy function blocks it at condition 1 and returns the reason to the model. The model then posts a draft in the thread, and runs the tool once a person approves it in a reply. In a thread where conversation has already gone back and forth, the code only checks whether a person has spoken after the agent’s last post, so whether to show a draft first is up to the model, following its instructions. The bot code writes one execution record for every action that affected an external system, and checks those records so that a restart or retry doesn’t create the same ticket twice.

I used the same approach for production database queries. In Part 1 the agent could query only the development database. Production data has columns designated as personal information, and I wanted to prevent the agent from reading those values and posting them in chat. This time, in consultation with the infrastructure team, the database account the agent uses was set up so that it cannot query personal-information columns at all, and on top of that I allowed production queries.

For the production database, the bot code looks not at meaning but at the query’s estimated cost. Write requests are denied by the policy function on the spot. For reads, the cost is measured from the query plan before execution, and a light query runs right away. A heavy one runs only if, after the agent’s last post, a person has written something or added a 👍. On the first message of a new thread, the model first posts the estimated cost and row count in the thread and waits for a person’s answer. A query whose cost couldn’t be measured is denied, because there’s no basis for treating it as light.

Now, when someone wants a production figure, they don’t have to ask a developer to run the query for them.

Code that connects to external systems lives in one place

I split the code into four parts.

  • Core (src/core): holds the contracts all the code keeps. The interfaces for external connections such as the storage tables, Slack, and the database are here, along with the list of tool names. Core imports from no other folder.
  • Composition root (main.ts, host.ts): the entry files that run when the agent starts. Objects that connect to external systems (Slack, the database, the model SDK, environment variables, timers) are created only here, and passed to the rest of the code in the shape of core’s interfaces.
  • Modules (10 folders under src): divide up what the bot code does, such as sessions, tool policy, storage tables, and the code workspace. They don’t create external connection objects themselves and use only what the composition root passes in.
  • Capability folders (9 folders under src/capabilities): under capabilities, which is one of the modules, each external service is attached as one folder. The HTTP clients and tools that call services like Jira and Sentry are here, and they receive even the fetch they use for requests, and the timeouts, from the composition root.

Divided this way, the composition root and the modules all import core, and core depends on nothing. In Spring terms, the composition root does by hand, in code and with no container, the constructor injection a DI container would do. Modules correspond to services that receive only interfaces, and capability folders to external API adapters. In tests, in-memory implementations are injected in place of the composition root to check session flows and policy. If a module imports a forbidden package, or imports another module against the set direction, a test fails.

Like external connections, tools can only be attached if they are on a fixed list. The built-in tools a thread session uses are fixed as file reading, search, shell, and a subagent it delegates code exploration to; beyond those, only tools the bot code itself defines are attached.

The structure holds up even when a coding agent changes it

Most of this repository’s code was also written by directing a coding agent. Of 149 commits excluding merge commits, 143 (as of early October) list Claude as a co-author. So I had to care as much about what the coding agent editing this repository could change as about what the model running inside the agent could do.

Coding agents usually work like this.

  • They copy code nearby that already works.
  • They add code to an existing file rather than creating a new one.
  • They pick the fastest way to get the build to pass.
  • They leave code in place, rather than delete it, when they don’t know where it’s used.
  • They build what was requested even when it conflicts with rules the system must keep.

These five come from the “Agent-friendly architecture” document of the Dune project, which Lauren Tan of Cursor introduced in a video. Telling a coding agent to be careful doesn’t change these habits much, so I structured the code so that the result is right even when a coding agent works this way. I made following the set pattern the easiest path, and made the build or tests fail when there is a forbidden dependency. New features were added as new files, not as branches in shared files. The external-connection rule above comes from the same thinking.

Here is how I applied it to agent-colleague.

  • For the 9 integrations (Jira, Sentry, DB, Bitbucket, Jenkins, the embedding server, ktlint, calendar, and Slack file download), each has one capability folder holding its client, configuration, and tests. Integrations that expose tools for the model keep those tools in the same folder, and a new integration is attached by creating one folder and adding one line to the capability list. Of the bot’s 33 tools, 23 are in these folders.

  • Rules aren’t left as documentation only; I turned them into tests that fail when a rule is broken. If capability folders import each other, a module is imported against the set direction, or an HTTP client is used outside a capability folder, a test fails.

  • Each tool’s name and kind, and the capability or module that registers it, are listed in a table in a single file. A tool that isn’t in the table doesn’t compile, so a coding agent can’t add a tool on the side that skips the policy check.

  • The rules have no exceptions. At first I kept an exception list, with counts, for code that seemed to have to live outside the composition root, such as a session timer or Slack file download. But the tests only checked the counts, so deleting one allowed timer and adding a new one passed, because the count was the same. After seeing this, I removed every exception. Timers and the SDK tool-server function are now passed in by the composition root, Slack file download moved into a capability folder, and casts that bypassed type checking were replaced with runtime value checks.

    Today every exception list is empty, so using even one timer outside the composition root fails a test. Merely writing the name setTimeout fails, using AbortSignal.timeout to put a timeout on an HTTP request fails, and putting an entry back into an exception list fails too.

  • I emptied the folder where integration code used to live under the old approach, and made a test fail if a file ever reappears there. This is to stop a coding agent from copying leftover old code and spreading the same problem.

Code changes are split between an implementation session and a review session

“Fix it and open a PR” is handled by a session that changes code (a code session), which works in the following order.

  1. The bot code creates an isolated temporary workspace.
  2. An implementation session changes the code.
  3. A fresh review session, which knows nothing about how the implementation went, reads only the instructions and the diff and writes down problems.
  4. If there are problems, the implementation session picks up again and addresses them.

The review session is separate so that the side that made the change isn’t the one giving its own work a favorable review. The review session gets no file-editing tools (Edit, Write), only reading, search, and shell. The three stages share one budget of model turns and cost.

Push and merge are constrained. Pushes go only to bot-only branches and the deploy branch, and PRs are opened only from bot-only branches. Merges happen only when a person asks, and only when a person, not a bot, has approved. The requester gets the PR link and a review summary in the thread, and from there it follows the usual code review flow.

Every shell command a code session runs executes inside the SDK’s sandbox. The sandbox is a restriction mechanism provided by the operating system: it limits which files a process and its child processes can read and write, and which network destinations they can reach. I used it because the bot code can’t screen in advance everything a shell command might do.

In a code session, the model composes and runs shell commands itself. Running the build and tests also executes the repository’s build scripts and dependency code, and text telling the model to run a command could be mixed into a code comment or issue body it reads. With the operating system restricting file and network scope regardless of what the command is, the model can’t change files outside the working folder or send company information off the machine, even if it makes a mistake or follows a bad instruction.

Even when the model runs builds and tests in the shell, the only two places it can write files are the working folder and the build cache folder. Network traffic goes only to addresses on an allowlist, and the allowlist is empty by default. The option that lets the model run a command with the sandbox off is disabled, and if any environment variable passed to a code session has a name that looks like a token or password, the bot code won’t start the job. The thread session’s shell runs in the same sandbox, with no network access at all.

Once network and file writes were blocked, the build wouldn’t run. In the first trial run, Gradle couldn’t write its cache to the home folder outside the working folder, and didn’t run at all. I created a dedicated Gradle home folder and allowed writes to it, and let it borrow, read-only, the dependencies already downloaded on the machine it runs on. The model is told to try an offline build first.

The Kotlin lint check (ktlint) couldn’t be run through Gradle, because the sandbox blocked the internal communication of the worker processes Gradle starts. Instead, the bot code, outside the sandbox, downloads in advance the ktlint binary of the version the repository uses, verifies its checksum, and tells the model the path to that binary. Pushing and creating the PR are also done by the bot code, not the model, after the session ends, so the repository server’s address is not on the allowlist.

Some restrictions weren’t in the original design and were added after I found problems during a one-day trial in the team channel. Instructions written in a personal settings file on my machine, where the agent runs, got mixed into the agent’s instructions, and connection details for external tools registered on my machine ended up in a code session’s conversation log. The same day, I changed sessions so they don’t read personal settings or external tool information.

Error alerts are handled with the same code session. When a Sentry alert is posted to the alert channel, the bot code creates one session per issue, and the model analyzes the cause and posts it in the thread. In designated backend repositories, it skips conditions 1 and 2 of the three above and goes on to fix the problem without waiting for a person’s answer. The fix proceeds in this order.

  1. Find the commit that caused it and the branch that commit came in on.
  2. Fix the code with a code session.
  3. Open a PR with the author of the commit that caused it as reviewer.
  4. Put the fix commit on the deploy branch.
  5. Deploy to the development and staging servers.

Errors that occur in production follow the same steps. However, the deploy tool only accepts the development and staging servers as targets in the first place, so nothing reaches production; the fix gets there in the next regular release or in a hotfix a person decides on.

Which repositories may be fixed without a person’s answer is decided by the policy function, a pure function. If the repository-list setting is emptied, nothing is fixed in any repository without a person’s answer, so if something goes wrong, automatic fixes can be stopped with one setting. And because the cause analysis is already attached when the alert appears, a developer doesn’t have to start by reading the stack trace.

I added a session that watches the channel, and search over past conversations

With one session per thread in place, one problem remained: a thread session can’t know what was said outside its thread. “That deploy from earlier” is usually outside the thread.

Channel sessions

I chose between two approaches. The first is to attach the channel’s last few dozen posts when a session starts. It’s simple, but it cuts off at however many posts are attached, so it can’t answer about anything beyond that. The second is to keep, for each channel, a session that continuously reads the conversation (a channel session). It costs more, because the model is called for every post, but the conversation the channel session has read can be handed to a thread as is. Only the second approach solves the problem above, so I chose channel sessions.

Each channel where auto-reply is allowed has one channel session, and every time a top-level post (a new post in the channel, not a thread reply) appears, it reads the post and decides. The only thing a channel session decides is whether to reply to that post. The only tool it has is “enter this thread,” so it cannot speak in Slack directly.

If it decides to reply, the bot code creates a new thread session that inherits the channel session’s conversation history as is, and that thread session writes the reply. When the channel has been quiet for a while, or a day has passed, the channel session is replaced with a new one, and what came before doesn’t carry over to the new channel session.

Finding past conversations by meaning

When a session is replaced, the model forgets what came before, so the agent needed a way to look up past conversations. The bot code stores every post in the channels the agent listens to in the database, including those that weren’t addressed to the agent. When a post is edited, it’s overwritten; when it’s deleted, only a deleted flag is set; and by default old posts aren’t removed, because this table exists to find a decision made six months ago.

The model looks through the stored conversations only when it judges it necessary, and when it does, it finds posts with similar meaning using embedding vectors. An embedding vector is a post’s meaning turned into a list of numbers. I compared two other approaches as well: a knowledge graph is strong at following relationships but wasn’t a fit for finding posts with similar meaning, and exact-text search can’t connect “timeout” with “I’m not getting a response,” so I ended up choosing embeddings.

The decision in Part 1 to leave embeddings out of code search stands. Code changes from branch to branch, so indexes would have to be maintained separately, but a conversation hardly changes once it’s posted. Embeddings are used only for conversations.

The bot code uses EmbeddingGemma 2, an embedding model released by Google, to turn each post into a vector of 768 numbers. The model is loaded in an embedding server that runs on the same Mac as the bot, and that server accepts requests only from within that Mac. The vectors are stored and searched in the PostgreSQL the agent was already using, with the pgvector extension added, so there’s no separate vector database.

Storing and retrieving run separately. The storing side doesn’t call the model and runs in this order.

  1. When a post appears in a channel the agent listens to, the bot code saves the original text in the channel-conversation table in PostgreSQL.
  2. Every 5 seconds, the bot code’s embedding job collects posts that don’t have a vector yet, a few dozen at a time.
  3. It sends them to the embedding server on the same Mac.
  4. It saves the returned vectors in the vector column of the same rows.

Posts under 10 characters, like “yep,” are skipped, because they end up vaguely close to any query. A reply like “That’s tomorrow morning” doesn’t say what it’s answering on its own, so each reply is embedded with two things prepended: the first 200 characters of the parent post and the first 200 characters of the reply immediately before it. The preceding reply is included because a reply like “OK, let’s go with that” responds to the reply just before it more than to the parent post. Deleted posts and replies under 10 characters are not prepended.

When a post changes, its vector is rebuilt. If someone edits a post, the bot code overwrites the original text and clears both that post’s vector and the vectors of replies that were built with that post prepended. The embedding job picks the cleared posts up again on its next pass. Deleted posts keep their row but are flagged as deleted and excluded from both search and embedding. The original Sentry alert posts that another bot puts in the alert channel aren’t embedded, because many similar-looking posts would pile up and could crowd out other search results. The analysis replies attached to those alerts are embedded, so they can serve questions like “Have we analyzed this error before?”

On the retrieving side, the model decides. For example, when the question “What did we decide about the release cadence last month?” arrives in a thread, it goes like this.

  1. The model judges that this question can’t be answered from the current thread alone and chooses the search terms itself. Here that would be something like “release cadence decision,” and the model calls the past-conversation search tool with it.
  2. The tool sends that query to the same embedding server used when storing posts and turns it into a vector of 768 numbers. It has to be made with the same model and the same length as the stored vectors to be comparable. The embedding server prepends a different short phrase to queries than to posts being stored; the model was trained to tell queries and documents apart that way.
  3. The tool queries PostgreSQL with that vector. pgvector measures the distance between the stored posts’ vectors and the query vector and returns 20 posts, closest first, that is, most similar in meaning. By default it searches the current channel, and when needed, all channels the agent listens to. Even when searching all channels, the alert channel is excluded and is searched only when the model names it explicitly. Each post comes with the first 300 characters of its body, the time it was written, and the thread it belongs to, and for a reply, the first 80 characters of the parent post as well.
  4. The 20 are candidates, and the model picks the ones that match the question. If the post it picks is a single reply from the middle of a thread, the surrounding context is missing, so the model can call the tool once more, naming that thread, to read the whole thread.
  5. The model answers on the basis of the conversations it found.

I didn’t preload the stored conversations into the prompt for every question. Most questions don’t need past conversations, and preloading would spend that many more tokens on every one.

At first I used OpenAI’s text-embedding-3-small and paid per use. In a 30-day period measured while still on OpenAI, 1,111 posts were embedded across the 8 channels the agent listens to, an average of 37 a day; at about 450,000 tokens a month (measured before prepending the preceding reply), the cost was under one cent (at $0.02 per million tokens).

In October I changed the model. Building vectors meant sending the original text of internal company Slack conversations to the OpenAI API as well, separately from Claude, which writes the answers. I didn’t think it was right to add one more place where internal conversations were sent. EmbeddingGemma 2 can be downloaded as model files and run directly, and its Apache 2.0 license allows use for company work, so I decided to run it on the Mac the bot runs on. Now, when vectors are built, the original conversation text doesn’t leave that Mac.

In the move, I set it to read only the first 1,024 tokens of each post, as this model counts them (about 1,800 Korean characters). Anything beyond that isn’t reflected in the vector; of the 2,265 posts in the production database, 2.5% were that long. The 2,156 existing vectors were rebuilt in about six and a half minutes with no failures, and the embedding server used about 1.9 GB of memory normally and about 3.4 GB at peak. I haven’t yet compared how search results differ from when I was using OpenAI.

Replying first to posts that weren’t addressed to the agent

I added auto-reply for the goal described earlier. A good share of the questions posted in a channel can be answered by looking at code or data, and for those, getting an answer right away matters more than who gives it. As described above, the person asking had to wait until the person who knew the answer came back. To cut that waiting time, even for questions that aren’t important or urgent, I had the agent reply to posts that weren’t addressed to it when it can help.

Which posts it steps into is decided jointly by code and model. The code passes to the channel session only posts that meet all of the following.

  • It was posted in a channel where auto-reply is allowed. DMs are not passed on.
  • It is a top-level post, not a thread reply.
  • A person wrote it. Posts from other bots or apps are not passed on.
  • It doesn’t mention the agent. A post that mentions the agent skips the channel session and goes straight to a thread session. A post that tags another person or team is passed on as is.
  • It isn’t in a thread the agent has already entered.

There is also one condition for stopping. The code counts the top-level posts that have gone by since the agent last entered a thread in that channel. If the agent doesn’t enter again before that count reaches a set number, the channel session stops judging. When the agent enters a new thread in that channel, the count starts over.

Whether to reply to a post it has been passed is up to the model. The instructions give the criterion (reply if the agent can help) together with when to stay quiet: when people are talking among themselves and haven’t asked the agent, when something already answered is asked again with no new information, and when the message is wrapping up a conversation. They also say that in a thread it has entered, the agent reads later posts even without a mention, but must not reply to something said to another person.

The criteria for staying quiet went in on the first day of the new structure. That day I found the agent could butt into replies people were exchanging with each other, and I fixed the instructions and restarted it right away. When something bothered the team in use, I tried to fix it the same day wherever possible.

Calling the model for every post raises an obvious cost question. I looked at it too and judged the cost manageable, for three reasons.

  • Fewer posts go to the model than you’d think. Posts that mention the agent and posts in threads the agent has entered go to thread sessions; top-level posts written by people in channels where auto-reply is allowed go to the channel session. The rest aren’t sent to the model at all and are only stored for past-conversation search.
  • Model prices came down. Opus 5.5, which the agent uses now, is cheaper than Opus 5: the base input price per million tokens went from $5 to $4, and cache reads from $0.50 to $0.20.
  • Instead of paying per use with an API key, the agent signs in with a Claude subscription account and calls the model within that plan’s usage. The same volume on pay-as-you-go API pricing would have added up to a fair amount, but as it is, model usage costs nothing beyond the subscription fee. The channel-session costs given in dollars below are also what the tokens used would come to at API list prices.

That doesn’t make tokens free. The subscription has usage limits too, so when usage gets close to the limit, the bot code stops new code jobs first. Even so, compared with the 10 minutes per question assumed earlier, I judged that the benefit of the agent answering first, like a colleague, outweighs spending this many tokens.

I also put a few cost-saving measures in place. As in the conditions above, only top-level posts written by people are passed to the channel session, and the stopping condition is there for the same reason. When handing off to a thread, the channel conversation isn’t summarized and re-sent; the thread session inherits the channel session’s history as is. The same session history can’t be written from two places at once, so the bot code starts the thread session right after the channel turn ends. At that point, the prefix the channel session just sent is still in the model provider’s prompt cache, so that part is billed at a tenth or less of the base input price.

I measured the actual cost too. In all 4 cases where it stepped in, the prefix sent by the channel session was read from cache: the whole prefix in 3 cases and part of it in 1. The input cost of the thread sessions’ first requests was about 30% lower, summed over the 4, than it would have been on a cache miss. That said, the inherited channel conversations were short, at 6,000 to 7,000 tokens. The first request also carries the extra cost of writing to the cache, for the first time, the 10,000 to 17,000 tokens newly added for the thread session, so the saving came to about $0.20 across the 4.

The bot code records cost per turn, along with whether the turn was one where the agent stepped in, and every morning posts yesterday’s and the last 7 days’ totals to an admin channel.

There’s an example from late September where the agent actually stepped in. When a post went up asking the app team to wire up the API for the Lounge share feature, the agent replied first, a minute and a half later. The post tagged the app team, but the model judged it could help and replied. The agent found, in the iOS and Android code, how the existing share feature records history and where that call was missing for Lounge sharing, and wrote it up. It also pointed out that the same call was missing from project sharing in the same menu.

There was also feedback that it was a nuisance. In the product development channel a colleague posted “The version going out this time is 3.2.0, right?”, and within 30 seconds the agent replied that, based on the version setting in the app code, it looked like 3.1.1.

When the colleague followed up that they were asking because the server needed to branch its response by version, the agent went on to post a summary of where the server code reads the app version and what to watch out for. The colleague then said, “Won’t this burn through tokens? And tokens aside, it feels like the conversation is getting really cluttered.”

The next version to ship is the app team’s call, so what the colleague wanted was confirmation from the app owner, not an answer found in the code.

It was one person’s feedback, but it came from a colleague who shares the channel and found it bothersome, so for now I’ve emptied the auto-reply channel list and turned the feature off. The agent still replies to posts that mention it and in threads it has already entered. Looking back, even when a question could be answered from the code, the person asking sometimes wanted confirmation from a specific person, and it was hard for the model to tell that difference from instructions alone.

Wrapping up

I estimate the questions the agent took on over 15 weeks at about 38 hours of developer time, on the assumption of an immediate response. In this redesign, what I cared about more than the number of questions was the range of work that can be handed to the agent. Because what may be executed is written down as code in the policy function, work that used to need a person to carry it out (creating tickets, changing code, querying the production database, responding to errors) can now be handed to the agent too. And because the new structure was built on that split from the start, with the model judging meaning and the code deciding execution, the code that manages conversation flow didn’t grow as features were added. On the other hand, auto-reply, where the final call on whether to step in was left to the model, is turned off for now because a colleague in the same channel found it bothersome.

It has been less than three weeks since the switch to the new structure, so I haven’t counted how much these features were used. Going forward, I plan to watch what the team actually hands over and add to the policy, one at a time, the things that are safe to hand over.
